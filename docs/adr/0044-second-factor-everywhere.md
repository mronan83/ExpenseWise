# ADR-0044: The second factor holds every request of someone with an authenticator, read from Supabase Auth's own record

While their organization has the second factor on, a session of someone whose sign-in has a verified authenticator, until it passes the code, gets nothing from the API but who they are and the organization's switches. Once a person has an authenticator, only an email they let in signs in: the one they first signed in with, once it passes its code, and any they let in from one that has; a session of another gets the same nothing, though receipts it emails are still filed, and one let in with no authenticator of its own gets it until it adds one and passes it (amended for #88, #90 and #91). Linking another sign-in needs the code from anyone with an authenticator, whatever the switch. The API learns who has one from Supabase Auth's own record of factors, through owner-run functions that answer yes or no, as each request finds its caller.

- **Status:** Accepted (every request held until the code, and linking a sign-in needing it, decided by product owner, Oct 5, Q41; a person's other emails held until each adds its own authenticator decided by product owner, Oct 5, Q43; reading Supabase Auth's record through one function, the two routes left open before the code, the linking rule applying whatever the switch, and how an email held for its own authenticator is asked and told, recommended, no objection yet; only an email let in signs in once a person has an authenticator, the others still forwarding receipts, and another let in from an email that passed its code, then adding its own, decided by product owner, Oct 5, Q44; observing the first by its first request past the code, letting another in for 24 hours, withdrawing one, what an email not let in may read and how it is told, and the owner's reset, recommended, no objection yet; only the email a person first signed in with let in on its own, which until then may add its own authenticator, and any other waiting to be let in from it, decided by product owner, Oct 5, Q45; that it is the sign-in the membership was made with, that unlinking it makes no other the first until the owner names one, that the app never changes it, that switching the second factor on from an email it would refuse is refused, and how a refused or held email is told, recommended, no objection yet)
- **Date:** 2026-10-05
- **Deciders:** Product owner (Q41, Q43, Q44, Q45); Claude (principal architect), for the design
- **Decision register:** D-46. Amends [ADR-0042](0042-second-factor.md), whose admin-only reach and GAP-33 it ends; builds on [ADR-0013](0013-supabase-platform.md) (Supabase Auth, our API for data), [ADR-0016](0016-several-sign-ins-per-person.md) (several sign-ins for one person) and [ADR-0035](0035-own-records-and-invite-links.md) (each request resolves its caller); closes GAP-33 (#85) and, amended, GAP-35 (#88), GAP-36 (#90) and GAP-37 (#91).

## Context

ADR-0042 asks for the code at sign-in in the app, and the API refuses admin actions and approving without it. A token from a password alone, used against the API directly, still read that person's records, changed their own and could link another sign-in (GAP-33). The product owner answered Q41: refuse every request of someone with an authenticator until they enter the code, and need it to link a sign-in.

A token says whether its session passed the code (`aal`), not whether its person has an authenticator. The app asks Supabase Auth in the browser (the session's next level is aal2 when a verified factor exists); the API needs the same fact. Five things shape how it gets it:

- **Supabase Auth keeps the factors** in `auth.mfa_factors`, one row per factor with its user and whether it is verified. People add and remove them from the browser straight to Supabase Auth; our API never sees it happen. Removing a verified one needs a session that passed the code, and the owner removes a lost one in Supabase's dashboard (the runbook).
- **The runtime connects as `expensewise_app`**, which can't bypass row-level security and holds no right on Supabase's `auth` schema; never as Supabase's `postgres` (CLAUDE.md). The schema owner, which runs the migrations and owns our definer functions, can read `auth.mfa_factors` on Supabase.
- **Tests and local development run on plain Postgres**, with no `auth` schema at all.
- **Every route already resolves its caller** through the workspace store, which records them for row-level security (ADR-0035); a store refuses to read a member's records without it.
- **A person may sign in with several emails** (ADR-0016). Each is its own Supabase Auth user, with its own authenticators and its own `aal`.

## Decision

1. **Supabase Auth's record, through one function.** Migration 0048 adds `sign_in_has_authenticator(user_id)`: whether that Supabase Auth user has a verified factor, any kind, as Supabase's own next level counts it, and nothing else: no factor's id, name, type or secret. It runs as the schema owner (SECURITY DEFINER), and only `expensewise_app` may call it. A user id that isn't a UUID isn't a Supabase Auth user, and plain Postgres has no Supabase Auth: both answer no. The migration reads `auth.mfa_factors` once when it exists, so a release whose schema owner couldn't read it fails there, not on every request. The API asks it in the same query that finds the caller's membership (`findSignedInMember`), so it costs no round trip.
2. **Once, as each request finds its caller.** Resolving the caller now admits them first: while the organization has the second factor on (the server's override first), a session at aal1 of someone whose sign-in has an authenticator is refused with 403 `second_factor_required` before anything of the organization is read or changed. The switch is read only in that case. No route can forget it; the two invite routes, which never needed a membership, now resolve it too. A test walks every operation in the contract.
3. **Open before the code: who they are, and the switches.** `GET /v1/me` names the signed-in user and nothing of an organization. `GET /v1/features` gives the organization's switches, which the code screen and the check in front of everything read to send someone there. Signing out is Supabase Auth's alone. Everything else is held, `POST /v1/me/organization` and Settings › Sign-ins among them. The health checks and the email webhook carry no person's token.
4. **Linking a sign-in needs the code, whatever the switch.** It adds a way in, so from someone with an authenticator it needs a session that passed it, even while the switch, or the server's override, is off. The app asks for the code where it asks for any, then links. Someone with none links as before, with proof of both sign-ins (FR-PLT-04).
5. **Someone with no authenticator is not asked**, as their session can't pass a code they don't have; admin actions still ask them to add one (ADR-0042). With the switch off, nothing changes for anyone, but point 4.
6. **Each sign-in by its own authenticators.** The code is asked of the token's own Supabase Auth user, as Supabase decides `aal`, so the API asks for a code exactly when the app sends the session to the code screen: never of one that has no code to enter. A person's other email with no authenticator of its own is held another way, until it adds one (see *A person's other emails*, below), and since #90 one they haven't let in is refused, its own authenticators counting for nothing (see *A person's emails let in*).
7. **In the app,** a read refused this way asks for the code with the same prompt as an admin action, and carries on once it is in; a download does too. The prompt never opens over the code screen, and gives way to it when a page's first reads were refused just before the session was sent there, so the code is asked once.

## A person's other emails (#88, Q43)

The product owner answered Q43 on Oct 5: hold a person's other email until it adds its own authenticator and enters its code, the app saying which email needs one.

8. **Held until it adds its own.** While the organization has the second factor on (the server's override first), a session of an email let in (point 13) with no verified authenticator of its own, of a person who has one on another email let in, is refused on every request with 403 `authenticator_required` before anything of the organization is read or changed. Since #90 an email that isn't let in is refused instead, and never offered to add one (point 13). The problem document names the email (`email`, and in its `detail`), so the app can say which one needs it. It is held whatever its session says: a token can still read aal2 for a while after its own last authenticator is removed, and what counts is whether the email has one now. Once it adds one in Supabase Auth and enters its code, its session reaches aal2 and passes; from then on it is an email with an authenticator, asked for its own code as in point 2. Off, nothing changes, linking included (point 4 asks only of an email with its own authenticator).
9. **One more function, over the person's sign-ins.** Migration 0050 adds `person_has_authenticator(user_id)`: whether any sign-in of the member this sign-in belongs to, this one or another, has a verified factor, as `sign_in_has_authenticator` answers for each. Yes or no, and nothing else: not which email has one, how many, or any email. It reads Supabase's record only through the first function, so what counts as a verified factor is decided in one place and no right on Supabase's `auth` schema is added; it runs as the schema owner because, before an organization is chosen, the app sees only the token's own sign-in (`own_sign_ins`), and only `expensewise_app` may call it. A sign-in no member has, and plain Postgres, answer no. The API asks it in the same query that finds the caller, beside the first, so it still costs no round trip; the switch is read only for an email held this way.
10. **The same two requests stay open.** Who is signed in (`GET /v1/me`) and the switches (`GET /v1/features`): Settings › Sign-ins adds an authenticator through Supabase Auth in the browser and reads only the switches from us, so the list is the code screen's, unchanged. The held email's own Settings › Sign-ins doesn't list the person's other emails.
11. **In the app,** a refusal this way never opens the code prompt, as there is no code to enter. A screen of its own, the only thing on screen like the prompt, says in plain words that this email, named, needs its own authenticator, with a button to Settings › Sign-ins and a way to sign out. Settings › Sign-ins says the same and offers adding one there, and opens the rest once its code is in.
12. **No lockout.** A held email can always add its own with its password alone, which is what Supabase allows an email with none. If a person's only authenticator is removed, by them or by the owner in Supabase for a lost phone, their other emails are free again on the next request; nothing of ours needs clearing, and the server's override turns all of it off (the runbook).

The hold stopped a stolen password used as it is, but couldn't tell the person adding an authenticator from someone else holding that email's password, who could add theirs and get past it: GAP-36, asked as Q44 and closed by letting a person's emails in (#90, below).

## A person's emails let in (#90, Q44)

The product owner answered Q44 on Oct 5: B, with the choice to add an authenticator to another email. Only an email with an authenticator signs in, the others still forward receipts, and the person may let another email in from one that has passed its code, after which it adds its own authenticator.

13. **Only an email let in signs in.** While the organization has the second factor on (the server's override first), once a person has an authenticator that counts, a session of an email of theirs that isn't let in is refused on every request with 403 `sign_in_not_let_in`, naming it, before anything of the organization is read or changed, whatever its session says. An authenticator counts on an email let in, or, before any is let in, on any of their emails; once one is let in, an authenticator added to an email that isn't counts for nothing, so its holder can't make a way in of their own. The same two requests stay open (point 10): the screen that says it isn't let in needs nothing else. Email-in is untouched: the webhook carries no person's token, and the sender is found by `member_for_sign_in_email`, which knows nothing of letting in, so an email from any address of theirs is filed. Off, nothing changes and nothing is recorded.
14. **The first is seen on its first request past its code.** While none of a person's emails is let in, a request from the email they first signed in with (point 21), with a verified authenticator of its own, at aal2, lets that email in as the request finds its caller, before the request goes on. (Until #91, any of their emails that did so first was let in.) A session at aal2 is Supabase Auth's own word that this sign-in passed a code of its own authenticator, and the API sees it on every request; it can't see an authenticator added or a code checked, which happen between the browser and Supabase. A Supabase Auth hook would be another service calling ours, with a secret and an endpoint to keep, and nothing to test it against here. The email's own authenticator is asked of Supabase's record too, as a token can read aal2 for a while after its last is removed. It costs no extra query (point 17), and it is checked again under a lock on the person, so a change to the person's emails in between is seen.
15. **Letting another in.** From an email let in, with an authenticator of its own, whose session passed the code, Settings › Sign-ins lets another of the person's emails in (`PUT /v1/me/sign-ins/{signInId}/let-in`). It waits: held as point 8 says until it adds its own authenticator and passes its code, which its first request at aal2 records; then it is let in for good. If it hasn't within 24 hours (`LET_IN_HOURS`, R-LET-IN-HOURS), letting it in lapses and it is refused again: letting an email in reopens, for that email, the window in which its password alone can add an authenticator (GAP-36), so the window is kept to a day, and letting it in again is one tap. From the same kind of session the person withdraws one (`DELETE` on the same path), which refuses it again; an email never lets itself in or withdraws itself. Unlinking an email takes its letting in with it.
16. **Kept beside the sign-ins, held by the database too.** `let_in_sign_ins` keeps one row per sign-in let in, by a composite key to `member_sign_ins` in the same organization, under forced row-level security: when it passed its code, or, while it waits, when it lapses. Each change appends `member_sign_in.let_in`, `member_sign_in.let_in_confirmed` or `member_sign_in.let_in_withdrawn` in the same transaction. A trigger, `enforce_let_in`, refuses any change by the app that isn't the person's own, from an email with an authenticator of its own whose session passed the code: the API sets `app.assurance_level` from the verified token for that transaction only, so a session at aal1 never changes who is let in, in the API or in the database. The schema owner, as for the runbook's reset, isn't held to it.
17. **Two more questions, in the same query.** `sign_in_let_in(user_id)` answers whether this sign-in is let in, waiting or not; `person_let_in(user_id)` whether the person has let in none, some without an authenticator now, or one with one. Each answers that and nothing else, runs as the schema owner because before an organization is chosen the app sees only its own sign-in, reads Supabase's record only through `sign_in_has_authenticator`, and is asked beside the other two as each request finds its caller. The domain's `admission` decides from the four answers and the session's level what the request meets.
18. **In the app,** a refusal this way never opens the code prompt: a screen of its own, the only thing on screen like the prompt, says in plain words that this email, named, isn't let in to sign in, that receipts sent from it are still filed, and how to let it in from the email that has the code, with Sign out; it is shown over Settings › Sign-ins too, where an email not let in is never offered an authenticator. Settings › Sign-ins on an email let in says which of the person's emails are let in, which waits and until when, and offers Let in and Withdraw once its session passed the code. An email not let in that has an authenticator of its own is still asked for its code at sign-in, as Supabase Auth offers it, before its screen. While none of the person's emails is let in, the screen says so instead (point 26).
19. **Recovery.** If a person loses the phone for the only email let in, the owner removes that authenticator in Supabase, as before: no email let in then has one, so none of the person's emails is asked anything more until the email let in adds a new one and passes it; from then on the others are refused again. Nothing of ours needs clearing, and the server's override still turns all of it off. If the email let in itself can't be used, its password lost or the account gone, the owner resets who is let in for that person with one SQL statement as the schema owner (the runbook); the email they first signed in with is then let in first again once it passes its code, and if that is the email that can't be used, the owner first names the one they still use as the first (point 23).
20. **The first could be someone else's, until #91.** Before a person's own email passed its code, for instance before they ever added an authenticator, whoever held the password of another email linked to them could add an authenticator to it, pass its code and be let in first. GAP-37, asked as Q45 and closed by letting in first only the email the person first signed in with (#91, below). Its screen still says to tell the owner if they never let another in, for an email let in that way before #91.

## Which email is let in first (#91, Q45)

The product owner answered Q45 on Oct 5: A, let in automatically only the email the person first signed in with; any other waits to be let in from it. Linking an email needs the passwords of both and, from someone with an authenticator, the code, so the email a person first signed in with is their own; a later one may be the one whose password leaked.

21. **Only the email first signed in with lets itself in.** While the organization has the second factor on and none of a person's emails is let in, the email they first signed in with is the one let in on its own, on its first request past its own code (point 14). If it has no authenticator of its own while another of theirs has one, it is held as point 8 holds an email (`authenticator_required`), never refused, so it can add its own on its password, which is its person's, and is then let in; until then it may add its own authenticator, as the answer says. Any other of their emails is refused with `sign_in_not_let_in` (point 13), at aal1 or aal2, its own authenticator and code included, and nothing is recorded: it waits to be let in from the first (point 15). Once one is let in, which was first no longer matters. Someone with one email is asked exactly as before: it is the one they first signed in with.
22. **The first is the sign-in the membership was made with.** That is `members.user_id`, which every member already keeps (migration 0007 backfilled the sign-ins from it as "the sign-in it was created with"): the email that signed in first and so made the person's organization, or the one that accepted their invite link, even if it had an empty organization of its own before, which it leaves (ADR-0035). Someone removed and invited back with that email is the same member and keeps it; back with another, they are a new member, whose first it is. Linking an email never changes it. The API learns it in the query that finds the caller, from the member row the caller's own sign-in already reads (`own_memberships`), so it needs no new function, no right the app hasn't got and no extra round trip; the domain's `admission` takes it as a fifth answer. The oldest of the person's sign-ins still linked would say the same until the first is unlinked, and then promote the next, the email Q45 is about; unlinking needs only a session, which before anyone has an authenticator is a password alone.
23. **An unlinked or lost first makes no other the first.** If the email first signed in with is unlinked, or can no longer be used, no other of the person's emails is let in on its own: once one of them has an authenticator, each is refused until the owner names, as the schema owner, the email the person still uses as the first and resets who is let in (the runbook, two statements). That can lock a person's own emails out until then, never let someone else's in.
24. **Held by the database too.** `enforce_let_in` (migration 0053) lets an email let itself in, past its code, only if it is the one its member was made with; and `keep_first_sign_in`, a trigger on `members`, refuses any change by the app to which sign-in a member was made with, whatever its session, so neither a password alone nor a session that passed the code makes another email the first. Only the schema owner changes it, by the runbook.
25. **Switching it on never refuses the email doing it.** ADR-0042 refuses switching the second factor on until the owner's own session passed the code. Since #91 that isn't enough: an owner at aal2 on an email other than the first, while none of theirs is let in, or on one not let in while another is, would be refused on the next request. Switching it on from such an email is refused with 409 `second_factor_would_refuse_you`, saying which email to switch it on from, and nothing is switched.
26. **In the app,** while none of the person's emails is let in, both refusals carry `noneLetIn: true`, and nothing else of the person's emails. The screen that says an email isn't let in then says that only the email first signed in with is let in on its own and this isn't it, even with an authenticator of its own, how to let it in from that one, and to tell the owner if they can no longer sign in with it. The screen that holds the first for its own authenticator, and Settings › Sign-ins, say it is the one let in first and that the others are let in from it, and no longer suggest signing in with the email that has an authenticator, which would be refused.
27. **Emails let in before #91 stay let in.** Each is a person's own choice or their first pass of a code, and the migration can't tell one let in first by someone else from one let in by its person. The runbook's query shows which of a person's emails is the first and which are let in, for the owner to reset if one let in first isn't theirs.

## Alternatives considered

| Option | Why not chosen |
| --- | --- |
| A record of our own, set when someone passes the code and cleared when they remove their last authenticator | Two records of one fact, which drift. Removing happens in the browser or Supabase's dashboard, never through our API, so ours would still say yes after the last one goes, and every later session, at aal1, would be refused: a lockout the runbook can't undo in Supabase alone. Clearing it from an aal1 session would let a stolen password clear it; clearing it beforehand from aal2 races the removal. And someone who adds one is unprotected until their first request at aal2. |
| Grant `expensewise_app` SELECT on `auth.mfa_factors` | The app would read every factor's secret, name and type, and depend on Supabase's grants on its own schema. |
| Ask Supabase Auth's admin API per request | A call to another service inline in a request, with the service key in the runtime (CLAUDE.md, ADR-0013). |
| Check every request in a middleware ahead of the routes | It knows no organization, so it would find the caller's membership a second time on every request. Finding the caller is where the organization, and so its switch, becomes known. |
| Hold a person's every sign-in with `second_factor_required` once any of them has an authenticator | The other sign-in can't pass a code until it adds its own, and the app, asking Supabase for that session, wouldn't send it to the code screen: every screen would be refused with nothing to enter. Asked as Q43; built with its own refusal, `authenticator_required`, that says which email needs one instead (point 8). |
| For a person's other emails, extend `sign_in_has_authenticator` to answer for the person | It answers for a sign-in, as Supabase decides `aal`, and the code is asked by it (point 6); answering for the person would ask the held email for a code it can't have. A second function keeps both facts, each yes or no. |
| Let a held email read its sign-ins and `POST /v1/me/organization`, so Settings › Sign-ins loads as it is | Adding an authenticator needs neither; the list of open requests would grow for a page, and a password alone would see the person's other emails. |
| Leave the linking rule to the switch | A password alone, while the switch is off, could still add an email it controls to someone with an authenticator, ready for the day it is switched on. |
| Confirm another email's new authenticator from one that passed its code (Q44 A) | The owner chose B: only an email let in signs in, with the choice to let another in, which then adds its own (#90). |
| Observe the first through a Supabase Auth hook when a code is verified | Another service calling ours, with a secret and an endpoint to keep, and nothing to test it against here; aal2 on the email's next request says the same, and the API already reads it. |
| Let in every email that has an authenticator when the switch goes on | It would let in an authenticator someone else added to an email with a stolen password, which is GAP-36 itself. |
| Letting in lasts until withdrawn, whether or not the email adds its own | An email let in and forgotten stays open to whoever has its password, who can add theirs at any time; 24 hours keep that window short, and letting it in again is one tap. |
| A column on `member_sign_ins` | Sign-ins are added and removed, never edited; a table of its own keeps the app's rights on sign-ins as they were, takes letting in away with its sign-in, and carries its own trigger. |
| Keep the first to pass its code (Q45 B) | The owner chose A: only the email first signed in with is let in automatically (#91). |
| Take the oldest of a person's sign-ins still linked as the first | The same until the first is unlinked; then the next is promoted, which may be the email whose password leaked, and unlinking needs only a session (point 22). |
| A column or table of its own saying which email is first | `members.user_id` already records it, set once as the member is made; a second record could drift from it, and the runbook would have two things to change. |
| Make the email that unlinks the first the new first | Before anyone has an authenticator, that session may be a password alone, so whoever holds another email's password could unlink the person's own and become the first: GAP-37 again. |
| Refuse unlinking the email first signed in with | A person whose first email is lost or no longer theirs couldn't remove it; it changes linking (FR-PLT-04) for everyone, not only while the second factor is on, and the owner's reset is needed either way. |

## Consequences

### Positive

- **A stolen password opens nothing** of an organization with the second factor on, for someone with an authenticator, through the app or the API, even for an email of theirs it could add an authenticator to (#90), and it is never let in first in their place: only the email they first signed in with is (#91).
- **Receipts still arrive from every address** a person has, let in or not.
- **Removing an authenticator takes effect on the next request**, by its person or by the owner for a lost one: nothing of ours to clear, and no lockout the runbook doesn't already undo.
- **One check, one place, no extra query.** It rides on finding the caller.

### Negative

- **The API reads a Supabase Auth table** through a definer function that depends on two of its columns (`user_id`, `status`). Supabase's own documentation reads them the same way for multi-factor policies; a release whose owner can't read them fails at the migration.
- **On plain Postgres, no one has an authenticator**, so the integration tests stand in for `auth.mfa_factors` where they need one, and the bench, which has none, never holds a request this way; its screens stand in for the refusals.
- **If the email a person first signed in with is unlinked or lost** before any of theirs is let in, none of their emails is let in on its own once one has an authenticator, until the owner names another as the first (point 23). Since #91 no one holding another email's password can be let in first (GAP-37 closed), and since #90 an authenticator added on a password alone to any other email counts for nothing (GAP-36 closed).
- **An email let in first by someone else before #91 stays let in** until the owner resets it (point 27).
- **A request at aal2 of an email waiting, or of the first while none is let in,** writes once, with its audit event; after that, nothing more is written.

## Exit path / reversibility

- **The admit step is the policy.** Narrowing it back to admin actions is one line in `app.ts`; the function stays harmless. Letting a person's other emails go again (Q43 B) is one change to `admission` in the domain, and `person_has_authenticator`, `sign_in_let_in`, `person_let_in` and `let_in_sign_ins` stay harmless too. Letting in first whichever email passes its code first again (Q45 B) is one change to `admission` and one to `enforce_let_in`; `keep_first_sign_in` stays harmless.
- **Another factor kind** (passkeys, phone) counts already: the function asks for any verified factor.
- **If Supabase moves its factors**, only the function changes.
